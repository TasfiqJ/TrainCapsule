## Goal
Produce one independently reviewable research bundle — a preregistered
version-2 query plan (`docs/evidence/T002/query-plan.json`), the findings
record (`docs/research/T002_name_trademark_check.md`), a version-2 evidence
manifest (`docs/evidence/T002/manifest.json`), and sanitized raw artifacts
(`docs/evidence/T002/raw/**`) — that states whether the product name
"TrainCapsule" and the CLI/package identifiers named in source-of-truth are
clear of trademark, package-registry, and domain conflicts, or documents the
exact conflicts found. This is evidence for human/legal review, not a legal
opinion, and not a rename.

## Scope
- In scope: a preregistered query plan; a primary-register trademark search
  for the product name; a package-registry name-availability/collision
  search on every registry source-of-truth actually names an intent to use;
  a domain-availability search for every candidate domain named in
  source-of-truth; and a labeled written record of findings with sources and
  query dates.
- Out of scope: renaming the product, registering any domain/package/
  trademark, or making a legal determination.

## Verification (deterministic gates)
Run from the repository root once `T002.yaml` is promoted to `tasks/T002.yaml`:

```text

bash scripts/gates/secret_scan.sh
bash scripts/gates/fast_quality.sh

```

`real_integration.sh T002` invokes `scripts/gates/output_and_integration_gate.py`,
which parses the research record (`parse_research_record`,
`validate_verdict_consistency`) and validates the evidence manifest
(`validate_evidence_manifest`) against the research stage's declared
`allowed_domains`. `validate_evidence_manifest` dispatches on the manifest's
own declared `version` field: a `version: 2` manifest (this revision's
target format) is checked against the stricter `_validate_v2_manifest` path,
which requires the preregistered `docs/evidence/T002/query-plan.json`, a
matching `query_plan_sha256` digest, and per-entry binding to a planned
`query_id`/`finding_id`. This is not a paper requirement: a prior research
attempt on this task already produced exactly this version-2 shape (see
"Revision history" below), so the gate code and the expected evidence shape
are proven compatible, not merely asserted compatible. The private gate
suite `traincapsule-integration-t002` (declared in
`factory/proposals/T002.yaml` and `factory/task_catalog.yaml`) runs
independently outside this repository; its result is authoritative and
cannot be weakened here.

## Failure / stop conditions (preserve UNKNOWN)
- Source-of-truth does not name any product name at all to check → stop the
  entire task; do not invent one.
- Source-of-truth names the product name or CLI token but does not name a
  specific package identifier or candidate domain for a given
  registry/registrar → do not invent the missing identifier; mark only the
  affected package/domain findings `UNKNOWN` with a documented reason, and
  still complete the checks source-of-truth does support (for example the
  trademark search on the named product name). As of this revision,
  source-of-truth names only the working codename "TrainCapsule" and the CLI
  token `traincapsule`; it does not name an intended package-registry
  publication target or a candidate domain, so most package/domain findings
  are expected to resolve `UNKNOWN` with that reason, not `CLEAR`.
- No network access is available to any primary trademark, package-registry,
  or domain-registrar source → mark the affected findings `UNKNOWN`, do not
  guess. `UNKNOWN` is a valid terminal state and is never converted to a
  pass; if every finding ends up `UNKNOWN` for this reason, AC-13 degrades
  to verifying the stop condition rather than requiring an impossible
  `CLEAR` finding.
- Any of these conditions is itself evidence to write into the record
  (as `UNKNOWN` findings with documented limitations), not a reason to omit
  the deliverable entirely, unless no product name exists at all to check.

## Revision history and known prior-failure causes (informational)
This is the seventh planning revision (`PLAN_T002_R7`) for T002. Prior
revisions repeatedly failed the bounded pipeline. This revision's own
in-repository evidence points to a specific, concrete cause that revision 6
did not fully close:

- **Revision 6 fixed the spec but the executed packet did not match it.**
  `factory/proposals/T002.yaml` at commit `bbd7034` ("plan t002") correctly
  removed per-stage `max_budget_usd`/`task_budget_tokens` ceilings and raised
  the research stage's `max_turns` to 40, exactly the fix documented by the
  prior revision's notes. However `tasks/T002.yaml` as written by the
  following "approve t002" commit (`4ee5f12`) — the file the controller
  actually queued and ran — still carried the *old*, restrictive research
  ceiling (`max_turns: 18`, `max_budget_usd: 3.8`, `task_budget_tokens:
  100000`), matching the packet preserved for reference at
  `factory/recovery/task-packets/T002-r7.yaml`. The approved-and-queued
  packet diverged from the reviewed proposal, so the same budget/turn
  starvation that revision 6 was supposed to fix was reintroduced at
  promotion time. This revision keeps the fix (no dollar/token ceilings on
  any stage, generous `max_turns` on every stage, `max_turns: 200` — the
  schema maximum — on the network-heavy research stage) and records this
  finding explicitly so the controller's proposal→task promotion step can be
  checked against it; the planner role cannot modify `tasks/**`, `tcfactory/**`,
  or the promotion logic itself.
- **The abandoned run already proves the version-2 evidence shape works.**
  Commit `ee816ec` ("chore: save t002 progress"), produced under the
  under-provisioned ceiling above at candidate `3a8832a`, contains a
  `docs/evidence/T002/manifest.json` with `"version": 2` and a
  `docs/evidence/T002/query-plan.json` — i.e., the research stage
  independently converged on the stricter version-2, preregistered-query-plan
  format that `tcfactory/research_policy.py` supports, rather than the
  version-1 format the prior spec's acceptance criteria described. That
  query-plan file is not covered by any of the previously declared three
  outputs (`docs/research/T002_name_trademark_check.md`,
  `docs/evidence/T002/manifest.json`, `docs/evidence/T002/raw/**`), so it
  would have tripped the "no file outside the declared outputs" acceptance
  criterion even though `allowed_paths` (`docs/evidence/T002/**`) permitted
  the write. This revision resolves the inconsistency by adopting the
  version-2 architecture explicitly: `docs/evidence/T002/query-plan.json` is
  now a fourth declared output, and the acceptance criteria describe the
  version-2 manifest/query-plan fields the validator (`_validate_v2_manifest`
  in `tcfactory/research_policy.py`) actually checks.
- **Source-of-truth does not name a package-registry or domain target.**
  The abandoned run's own preregistered findings (`SOT-1`, `SOT-2`) recorded
  that no package-registry publication target or candidate domain is named
  anywhere in source-of-truth — only the working codename "TrainCapsule" and
  the CLI token `traincapsule`. This revision states that expectation
  directly in the stop conditions so a future research stage does not treat
  a legitimate `UNKNOWN` result as a defect to work around.
- Earlier revisions (documented by revision 6) had also fixed a broken
  `source_of_truth` list pointing at non-existent files and an
  unconditional adversary re-check requirement that was unsatisfiable under
  an all-`UNKNOWN` stop condition; both fixes are preserved unchanged in
  this revision.
- **A repository-wide candidate-quality detector, not a declared gate, ended
  the previous attempt at this revision.** `enforce_candidate_quality` in
  `tcfactory/quality_policy.py` scans every removed line in the candidate diff
  for the substring `assert`, case-insensitively, and rejects the candidate
  when `allow_test_changes` is false. It runs on every candidate regardless of
  which gates a packet declares, so satisfying it is mandatory even though it
  is not one of this task's four named gates. The previous attempt merely
  reworded one prose sentence that happened to contain the word "asserted",
  and the reworded-away line was counted as a deleted test assertion. The
  specification itself was sound and the declared `proposal-policy` gate
  passed. Two sentences in this bundle still contain that substring — the
  positive-control acceptance criterion in `factory/proposals/T002.yaml` and
  the compatibility note in "Verification" above — so any later revision must
  leave those two lines byte-identical unless it carries explicit test-change
  authority. This revision left both untouched and confirmed the candidate
  scan reports no violations.
- **One ledger seed field is deliberately overridden, recorded here rather
  than silently.** `factory/feature_ledger.yaml` seeds T002 with
  `commit_type: feat`. Every declared output of this task is a document or
  evidence artifact under `docs/`, so this packet declares `commit_type: docs`,
  the truthful label for the change it produces. This is a considered planner
  decision, not promotion drift; it should not be reverted to `feat` on the
  assumption that the packet diverged from the ledger by accident.
